# Карта соединений Linux-роутера или сервера

Сервис работает на самой машине. Он читает таблицу соединений ядра (conntrack), сокеты, интерфейсы
и правила iptables, определяет места по своей копии DB-IP и отдаёт карту в браузер.
Нужны только Python 3.9+ (стандартная библиотека) и стандартные пакеты Debian и Ubuntu.

Два режима, выбираются в `.env`:

- `mode=router` — машина с WAN и LAN (две сетевые карты, NAT). Слева на карте устройства LAN,
  справа мир. Устройства видны по таблице соседей (ARP и NDP), подписи берутся из файла имён.
- `mode=host` — один сервер, обычно в облаке. Вместо устройств на карте процессы сервера
  (sshd, nginx, …) и клиенты VPN, если сервер их обслуживает.

## Установка

```
sudo apt install python3 conntrack       # iproute2 и iptables обычно уже стоят
sudo cp -r linux-api /opt/linux-map && cd /opt/linux-map
sudo cp .env.example .env && sudo nano .env
sudo cp names.conf.example names.conf    # по желанию, подписи устройств
sudo ./start.sh                          # в этом окне; остановить Ctrl+C
```

При первом запуске скачиваются базы (около 95 МБ, см. ниже), затем сервис один раз строит их кэш
(около минуты, с IPv6 дольше) и печатает адрес карты.

Как служба systemd:

```
sudo cp linux-map.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now linux-map
journalctl -u linux-map -f
```

В `linux-map.service` путь `/opt/linux-map`; поправьте, если проект лежит в другом месте.

Сервис запускается от root: без root не читаются conntrack, `iptables-save` и имена процессов в `ss`.
Сервис ничего не меняет в системе, кроме одного случая: `conntrack_acct=on` включает
`net.netfilter.nf_conntrack_acct=1` (см. ниже).

### Docker

Контейнер работает только с сетью, процессами и файловой системой хоста. Изоляции почти нет:
Docker здесь — способ упаковки, чтобы не ставить Python и утилиты на хост. Для роутера на Debian или Ubuntu
проще служба systemd.

```
cp .env.example .env                      # режим, WAN, где слушать карту
cp names.conf.example names.conf          # файл нужен: без него Docker создаст на его месте каталог
docker compose up -d --build
docker compose logs -f                    # первый старт: скачивание ~95 МБ и сборка кэша, около двух минут
```

Что задаёт `docker-compose.yml` и зачем:

| Настройка | Зачем |
|---|---|
| `network_mode: host` | интерфейсы, маршруты, соседи и conntrack хоста; `http_*` в `.env` работают как на хосте, `ports` не нужен |
| `pid: host` | имена процессов хоста в `ss` |
| `uts: host` | имя хоста в верхней панели |
| `cap_add: NET_ADMIN` | `conntrack -L/-E`, `iptables-save` |
| `cap_add: SYS_PTRACE`, `DAC_READ_SEARCH`, `apparmor=unconfined` | `ss -p` видит сокеты процессов хоста |
| `/:/host:ro` | `/etc/os-release`, `/etc/hosts`, занятость диска, статус-файлы OpenVPN (переменная `HOST_ROOT=/host`) |
| `./geo`, `./oui` | базы хранятся на хосте и переживают пересборку образа |

`/proc` и `/sys` контейнера при общей сети и PID показывают хост: процессор, память, время работы,
температура и счётчики интерфейсов верные без подключений.

Учёт байт conntrack: в обычном контейнере `/proc/sys` только для чтения, и `conntrack_acct=on` не сработает.
Включите его один раз на хосте (раздел «Учёт байт conntrack») или раскомментируйте `privileged: true`.

Пути в `openvpn_status` пишутся как на хосте: сервис сам добавит `/host`.

В образе Debian 12 с `iptables` 1.8.9 в вариантах nft и legacy: сервис берёт тот вариант, в котором
есть правила. Если iptables на хосте заметно новее (Arch, Manjaro, свежая Fedora), старый `iptables-nft-save`
в образе может не понять часть правил. Такие правила пропускаются, строка помечается как приблизительная.

Обновить базы: `docker compose exec linux-map python fetch_data.py --update`, затем `docker compose restart`.

### Доступ к карте

Авторизации в сервисе нет. Карта открывается так:

- **роутер:** `http_bind_interface=eth1` — сервис слушает только на адресе LAN-интерфейса;
- **облако:** `http_host=127.0.0.1` (по умолчанию) и туннель `ssh -L 8787:127.0.0.1:8787 user@server`,
  затем в браузере http://127.0.0.1:8787;
- **из интернета:** только через обратный прокси с TLS и авторизацией (nginx, Caddy) перед `127.0.0.1:8787`.
  Поток событий `/api/events` — это SSE: в nginx для него нужны `proxy_buffering off;` и длинный `proxy_read_timeout`.

Для браузера нужен интернет: шрифты, d3 и контуры карты грузятся с CDN.

## Настройки: `.env`

Шаблон с пояснениями — `.env.example`. Любой ключ можно переопределить переменной окружения в верхнем
регистре: `POLL_INTERVAL=10 ./start.sh`.

| Ключ | По умолчанию | Что это |
|---|---|---|
| `mode` | `router` | `router` или `host` |
| `wan_interface` | пусто | WAN-интерфейс; пусто — интерфейс маршрута по умолчанию |
| `lan_interfaces` | пусто | только `router`: LAN-интерфейсы через запятую; пусто — все, кроме WAN, `lo`, docker, veth |
| `http_bind_interface` | пусто | слушать на IPv4-адресе этого интерфейса; важнее `http_host` |
| `http_host` | `127.0.0.1` | адрес карты, если `http_bind_interface` пуст |
| `http_port` | `8787` | порт карты |
| `poll_interval` | `30` | секунд между опросами (минимум 5) |
| `config_interval` | `300` | секунд между перечитыванием адресов, firewall, сокетов и файла имён |
| `public_ip` | пусто | пусто — адрес WAN, а если он серый, запрос к ifconfig.me (запасной — api.ipify.org) раз в `config_interval`; адрес — взять его; `off` — не спрашивать |
| `location` | пусто | `широта,долгота` машины, если DB-IP не знает место внешнего адреса |
| `names_file` | `names.conf` | файл имён |
| `conntrack_acct` | `off` | `on` — включить учёт байт conntrack при старте (в шаблоне `on`) |
| `conntrack_events` | `on` | следить за `conntrack -E`: старты и концы соединений сразу, а не раз в опрос |
| `openvpn_status` | пусто | файлы статуса OpenVPN через запятую; пусто — искать в обычных местах |
| `ipv6` | `auto` | `auto` — IPv6, если на WAN есть глобальный IPv6-адрес; `on`; `off` |

Интерфейсы `tun*`, `tap*`, `wg*` в обоих режимах считаются внутренними: трафик VPN-клиентов через
машину виден как трафик устройств.

## Файл имён

`names.conf` (шаблон `names.conf.example`). Строка: `адрес имя [тип]`, имя с пробелами — в кавычках.

```
aa:bb:cc:11:22:33     "NAS в кладовке"   nas
192.168.1.20          Принтер            printer
10.8.0.0/24           VPN                pc
203.0.113.10          "Офис Москва"
```

- Адрес: MAC, IP (v4 или v6) или сеть. MAC надёжнее для устройств LAN: имя сохранится при смене IP.
- Сеть подписывает все адреса в ней с номером хоста: «VPN .5».
- Тип задаёт значок и категорию: `pc`, `phone`, `nas`, `server`, `camera`, `printer`, `tv`, `iot`, `ap`, `speaker`, `vacuum`.
- Внешние адреса тоже можно подписать: имя показывается вместо организации.
- Порядок поиска: MAC, точный IP, самая узкая сеть, клиент OpenVPN, `/etc/hosts`, обратный DNS,
  производитель по MAC, сам адрес.
- Файл перечитывается при изменении каждые `config_interval` секунд, перезапуск не нужен.

## OpenVPN

Если на машине работает сервер OpenVPN со статус-файлом, сервис читает из него клиентов:

- туннельные адреса клиентов подписываются их Common Name (если нет имени в `names.conf`);
- входящее соединение клиента к серверу OpenVPN отмечается категорией «VPN и служебное», а не как атака;
- список клиентов с внешним адресом, местом и временем подключения — во вкладке «Периметр»
  и во всплывающей подсказке ячейки «Туннели».

Статус-файл ищется в `/run/openvpn-server/*.log` (юнит `openvpn-server@`), `/run/openvpn/*.status`
(юнит `openvpn@`), `/var/log/openvpn/*status*`, `/etc/openvpn/*status*`. Если у вас другой путь, задайте его
в `openvpn_status`. Если статус-файла нет, добавьте в конфиг сервера `status /run/openvpn-server/status-NAME.log 10`.
Понимаются форматы `status-version` 1, 2 и 3. Файл, который не менялся 10 минут, пропускается.

OpenVPN-клиент на этой машине виден как интерфейс `tun*` в ячейке «Туннели».

## Что на карте

- **Дуги наружу** — соединения устройств LAN и самой машины; цвет по категории (сервисы, P2P, облака
  умного дома, VPN, в режиме `router` — «Сам роутер», прочее), толщина — по скорости.
- **Подключения снаружи** — пунктирные дуги к машине и пульсирующее кольцо у источника: SSH, веб,
  непрерывный ping. Клиенты OpenVPN — розовые, с именем клиента.
- **Сканы** — жёлтые мерцающие ромбы без дуг и короткие искры к машине. Подключение считается сканом, если:
  - ответа не было, или TCP-рукопожатие не завершилось (`SYN_RECV`, `UNREPLIED`);
  - при включённом учёте байт: ping из 1–3 пакетов или TCP без `[ASSURED]` не больше чем из 6 пакетов;
  - источник за час трогал 3 и больше портов, а прочного соединения (`[ASSURED]`) у него нет.

  Исследовательские сканеры (Censys, Shodan, Palo Alto и подобные, по имени организации в ASN) — серые.
  Адреса из `names.conf` сканерами не считаются никогда: впишите туда свой мониторинг (Zabbix, Prometheus),
  офисы и другие свои серверы.

  Новое входящее соединение из потока `conntrack -E` сначала не показывается: в момент NEW любое
  TCP-соединение ещё без ответа, и сессию не отличить от скана. Решение принимается на ближайшем опросе
  (по текущему состоянию в таблице) или по событию DESTROY, если соединение успело закрыться: TCP без
  `[ASSURED]` — скан. Такие короткие соединения появляются на карте кометой или искрой и в ленте.
- **Бегущие точки** — трафик за последний опрос. Соединение без трафика остаётся дугой без точек.
- Места ближе ~34 px к машине стоят кольцом вокруг неё с общей подписью «рядом: …».
- **Плашки слева**: «Кто на сервере» (или «на роутере») и «Порты из интернета» (см. ниже).
- **Справа**: вкладки «Направления», «Процессы» или «Устройства», «Страны», «Периметр» (подключения
  сейчас, сканы, сканеры за час по организациям, клиенты OpenVPN). Под вкладками — «Активные
  соединения»: всё, что передавало данные за последний опрос.
- **Лента внизу** с фильтром «все / входящие / исходящие / сканы»: новые соединения и, раз в опрос,
  продолжающиеся соединения с трафиком (бледнее, со скоростью в конце).

Имена устройств без записи в `names.conf`, `/etc/hosts` и обратном DNS: тип по производителю сетевой
карты, производитель и конец MAC, например «камера Hikvision …C6:EE»; для случайного MAC — «скрытый MAC …44:55».

## Кто на сервере

- **Открытые сессии** — `who` (utmp): пользователь, терминал, адрес, сколько времени назад вошёл.
- **SSH за последний час** — входы, неверные пароли или ключи, несуществующие пользователи, выходы
  из журнала sshd. Повторы с одного адреса сворачиваются: «root · неверный пароль ×40».
  Источник: `journalctl` (читается по курсору, без повторов) или `/var/log/auth.log`, `/var/log/secure`.
- Неудачные входы подсвечивают плашку жёлтым и называют адрес, который перебирает больше всех.
  В режиме `router` вход не из локальной сети подсвечивает плашку красным; на облачном сервере
  все входы снаружи, поэтому там это не тревога.

В Docker `who` читает `/host/run/utmp`. `journalctl` в образе нет, поэтому журнал берётся из
`/host/var/log/auth.log`; если на хосте нет rsyslog (только журнал systemd), входы не видны.

## Что опрашивается

Каждые `poll_interval` секунд:

- `/proc/stat`, `/proc/meminfo`, `/proc/loadavg`, `/proc/uptime`, температура из `/sys/class/thermal`,
  занятость `/`;
- счётчики WAN из `/sys/class/net/<wan>/statistics`;
- соседи `ip -j neigh` на LAN-интерфейсах;
- статус-файлы OpenVPN;
- сокеты `ss -tunpi`: имена процессов;
- открытые сессии `who` и новые сообщения sshd;
- вся таблица соединений: `conntrack -L` (IPv4 и IPv6) или `/proc/net/nf_conntrack`.

Соединения сравниваются по исходному кортежу (протокол, адреса, порты): новая запись — «старт»,
пропавшая — «конец», разница счётчиков байт — текущая скорость. Между опросами `conntrack -E`
сообщает о стартах и концах сразу, браузер получает их раз в секунду. Поэтому видны и короткие
соединения, которые открылись и закрылись между опросами.

Каждые `config_interval` секунд: адреса и маршруты (`ip -j addr`, `ip -j route`), внешний адрес,
файл имён, слушающие сокеты (`ss -tulnp`) и правила (`iptables-save`, `ip6tables-save`).

Верхняя панель: имя машины, платформа, ОС и ядро, время работы, процессор (загрузка, ядра,
температура, load average в подсказке), память (swap в подсказке), диск `/`, внешний IP (отметка
двойного NAT, если WAN-адрес частный, а внешний известен), скорость WAN и трафик с запуска, загрузка
канала (если известна скорость порта), соединения и заполнение таблицы conntrack, устройства LAN,
туннели. В подсказке внешнего IP — шлюз, DNS и сети LAN.

### Учёт байт conntrack

По умолчанию ядро не считает байты соединений, и скорости на карте нулевые. `conntrack_acct=on`
выставляет `net.netfilter.nf_conntrack_acct=1` при старте; счётчики появятся у соединений, открытых
после этого. Постоянно (без сервиса):

```
echo net.netfilter.nf_conntrack_acct=1 | sudo tee /etc/sysctl.d/90-conntrack-acct.conf
sudo sysctl --system
```

### Без таблицы conntrack

Таблица существует, только когда загружен модуль `nf_conntrack`. Его загружает любое правило firewall
с состоянием: ufw, Docker, `-m conntrack`. На голой облачной машине без firewall таблицы может не быть.
Тогда сервис берёт соединения из `ss`: видны только сокеты самой машины, скорость только для TCP.

## Плашка портов

Для каждого процесса со слушающим сокетом:

- привязка к loopback или LAN-адресу — «только локально», из интернета недоступен;
- привязка к `0.0.0.0`, `::` или WAN-адресу — проход нового пакета с WAN по цепочке `INPUT`
  с переходами в пользовательские цепочки (ufw хранит правила в `ufw-before-input`, `ufw-user-input` и других):
  - красный — firewall пропускает всех;
  - жёлтый — пропускает только адреса из правил с `-s` или ipset;
  - зелёный — отбрасывает.
- Правила `limit` ufw (и другие с ограничением частоты) не закрывают порт: первый пакет проходит.
- Правила с условиями, которые сервис не разбирает, пропускаются, строка помечается как приблизительная.

Строка плашки начинается с порта — это то, что видно из интернета; под ним — кто его открыл и куда он
ведёт: `2222/tcp` / `sshd`, `10051/tcp` / `docker → контейнер zabbix-server (172.18.0.3:10051)`,
`8022/tcp` / `DNAT → 192.168.1.20:22`. Порядок — по опасности: открытые, ограниченные по адресам, закрытые;
внутри группы первыми идут порты с подключениями. Порты одного процесса на `127.0.0.1` и на `0.0.0.0`
разделяются: локальные уходят в строку «только локально».

Пробросы портов — правила DNAT в `nat PREROUTING`, в том числе опубликованные порты Docker (`docker` —
если правило в цепочке `DOCKER` или адрес принадлежит контейнеру; имена контейнеров берутся из `docker ps`
и `docker inspect`, без Docker CLI остаётся только адрес). Такие пакеты идут через `FORWARD`, а не `INPUT`,
и фильтр `FORWARD` не проверяется.

Если правила есть одновременно в iptables-legacy и iptables-nft, проверяются оба набора. Если в nftables
есть собственные таблицы (не созданные через iptables, например firewalld), вывод помечается как приблизительный.

Числа справа — подключения к порту сейчас (без сканов) и источники сканов за последний час.
Ниже в раскрытой плашке — список «Сейчас подключены»: кто, откуда, к какому процессу и с какой скоростью.

## Файлы

- `server.py` — HTTP-сервер: страница, `/api/state` (снимок), `/api/events` (поток событий, SSE).
- `collector.py` — опрос машины, сравнение снимков, скорости, события conntrack, счётчики входящих за час.
- `conntrack.py` — таблица соединений и поток событий.
- `sockets.py` — сокеты и процессы из `ss`.
- `sysinfo.py` — ОС, процессор, память, диск, интерфейсы, маршруты, DNS.
- `firewall.py` — разбор `iptables-save`; `ports.py` — строки плашки портов.
- `names.py` — файл имён, соседи, `/etc/hosts`, обратный DNS.
- `openvpn.py` — клиенты из статус-файлов OpenVPN.

## Ограничения

- Истории нет: всё в памяти, после перезапуска счётчики начинаются заново.
- Скорость соединения — среднее за последний интервал опроса.
- Входящие подключения видны, только если firewall их пропустил: отброшенные пакеты в conntrack не попадают.
- Без `conntrack` (пакет) событий нет: короткие соединения между опросами не видны.
- IPv6 в базах мест заметно увеличивает память и время первой сборки кэша, поэтому включается только при IPv6 на WAN.
- Проход через `FORWARD` для пробросов и таблицы nftables вне iptables не проверяются.
- Без учёта байт conntrack (`nf_conntrack_acct=0`) сканы определяются только по ответу и числу портов:
  короткий ping и недозавершённые TCP-сессии не отличаются от настоящих.
